## 一、问题定界（已核实）

### 1.1 识图失败（3 个叠加缺陷）

| # | 缺陷 | 证据 |
| :-- | :-- | :-- |
| V1 | **自动发现选错模型**：`resolveVisionModel` 精确正则 `/Qwen3\.6\s*Plus/i` 匹配不到真实模型 id `qwen3.6-plus`（连字符 vs 空格），回退"任意 qwen"命中 `qwen3.7-max`；pi-ai 出厂目录中 **`qwen3.7-max` 是纯文本模型（`input:["text"]`）**，`qwen3.6-plus` 才是视觉模型（`input:["text","image"]`） | pi-ai 目录 `node_modules/@earendil-works/pi-ai/dist/providers/data/opencode-go.json`；`outputs/visionCache/runs/vision-runs.jsonl` 7 次调用 `provider:"opencode-go", model:"qwen3.7-max"` |
| V2 | **消息契约不符**：插件传 OpenAI 线格式 `{type:'image', source:{type:'base64'…}}` 与裸对象 message；DSH 的 `llm.stream` 要求规范 `Message`（`content: ContentBlock[]`），图片块必须是 `{type:'image', attachment: ImageAttachmentRef}`（由 `attachments.saveImage()` 生成、`readImage(block.attachment)` 读取） | `dsh-llm/lib/types/types.d.ts`、`dsh-llm-pi-ai/lib/index.js:229-249, 826-830`、`dsh-attachment/lib/types/index.d.ts` |
| V3 | **错误被协议吞掉 + 日志只记症状**：`llm.stream` 把适配器异常归一化为终态 `finish` 错误块（不 throw、不产出文本）；插件不读 finish 块 → `rawText=''` → `JSON.parse('')` → `json_parse`；run 日志丢失真正失败码（适配器门禁为 `UNSUPPORTED_CONTENT` 或 `readImage(undefined)` 抛错） | `dsh-llm/lib/index.js:1327-1345`（`adapterStream` → `adapterFailureChunk`）；`vision-runs.jsonl` 7 条 `rawText:""`、耗时 2–13ms |

## 二、方案 A：视觉识别修复（改预设插件 + 预设配置，宿主零改动）

### A1 目标与验收

- 目标：涉图题经 `geo_solve` / `geo_extract_images` 能拿到**真实可用的图转录**（Markdown 含 observed/uncertain），失败时有**真实原因、可复现、不静默**。
- 验收：
  1. 对皖 2025 综合 G17 `fig_1`（`E:\知识图谱\obsidian_vault\90_附件\题目图片\安徽\2025\2025-安徽-地理-2025年安徽高考地理真题-综合G17__shared__01.png`）跑通一次真实转录：`vision-runs.jsonl` 出现 `status:"success"`、`schemaOk:true`、含 `rawText` 与 `resultSummary`；
  2. 第二次调用命中 `imageHash` 缓存（`cacheHit:true`）；
  3. `geo_solve` 返回的 `vision.markdown` 非空、`vision.usable:true`；
  4. 无视觉能力模型时返回显式 `degraded` + 原因，不再静默。

### A2 改动 1：模型选择修正（`plugins/vision/index.js` 的 `resolveVisionModel`）

- 匹配改为**先按显示名、再按 id 规范化匹配**（`name="Qwen3.6 Plus"`、`id="qwen3.6-plus"` 连字符），并加**能力校验**：选中后调 `llm.resolveModelInfo(provider, model)`，`inputModalities` 必须含 `image`，否则明确失败（带候选与原因），不再静默回退。
- 配置固定（推荐）：`agent.cordis.yml` geo-vision 行显式 `provider: opencode-go, model: qwen3.6-plus`；自动发现仅作兜底；`FORCE_MODEL` 默认值改为 `'qwen3.6-plus'`。

### A3 改动 2：规范消息契约（`transcribeOne`）

- 用 `ctx.get('attachments')`（与 `ctx.get('llm')` 同机制；宿主 `dsh-base` bundle 已挂 `attachment-local`）把图字节落地为引用，再构造规范内容块与消息：

```js
const ref = await attachments.saveImage({ data: bytes, mediaType: contentType, name: img.caption || img.imageId });
const content = [{ type: 'image', attachment: ref }, { type: 'text', text: prompt }];
const messages = [{ id: 'msg-' + randomId(), role: 'user', content, source: { kind: 'user' } }];
```

- 删除插件自写 `bytesToBase64`（base64 由适配器内部处理）；图片字节上限取 `min(MAX_BYTES, attachments.imageLimits.maxImageBytes)`，超限明确降级。

### A4 改动 3：流消费 + 真实错误上报

- 消费类型化 chunk（`text-delta` / `reasoning-delta` 累积文本），并把 `finish` 错误块抛成可记录的真实错误（`vision_llm <code>: <message>`）；对可重试错误码重试 1 次。
- 结果：run 日志将出现 `UNSUPPORTED_CONTENT` / `UNKNOWN_MODEL` / 附件错误等**真实失败码**，不再只有 `json_parse` 下游症状。

### A5 改动 4：降级语义（不静默）

- `extract()` 返回增加 `visionOk`：全部图失败 → `visionOk:false` + `degraded[]`（含真实原因）+ `markdown:''`；部分成功 → `visionOk:true` 但 markdown 仅成功图。
- 单图失败保留 `[图] 图注` 兜底（`extractMaterial` 已保留图注行，无需改）。
- `no_vision_model` 分支补候选清单与失败原因。

### A6 改动 5：`geo_solve` 接入语义（`plugins/analysis/index.js`）

- 仅当 `vision.markdown` 非空才视为可用（`vision.usable:true`）；否则返回显式 `degraded` 摘要，由 solver 技能按"涉图但图像未提取"规则以图注解题。

### A7 验证步骤

1. 静态：`npm run verify:geo -- --source`（语法 / ESM 导入 / apply 冒烟 / 双副本哈希 / YAML / isolate / 路由）；纯函数单测补模型选择用例（`qwen3.7-max` 必须被拒绝、`qwen3.6-plus` 必须被选中）。
2. 动态（需 DSH 重启 + geo-teacher 新会话）：对皖 G17 调 `geo_extract_images` → 检查 `vision-runs.jsonl` 出现 success 记录 → 再次调用命中缓存 → `geo_solve` 自动带图输出非空 markdown。

## 三、方案 B：整体工作流程修复

### B1 目标与验收

- 目标：**solve 阶段彻底不接触任何答案/解析派生信息**；solve→judge→explain 成为真正有状态衔接的流水线；工具调用次数与上下文体积显著下降。
- 验收：① 抽查 5 道选择题，`geo_solve` 返回中无 `answer/analysis` 字段、scaffold 无解析派生线索；② 独立性指标（仅凭 solve 输出判正误）可度量；③ 单题讲题流程工具往返 ≤ 3 次且不重复携带同一材料。

### B2 改动 1：堵 solver 答案泄漏（`plugins/core/index.js`）

- `solutionScaffold()`：**删除 `distractorClues`（解析派生）**；保留 `questionFramework`/`thinkingModes`（由题干派生，安全）与 `dimensionScan`（由材料派生，安全）。干扰项排除论证交由 judge 阶段开放。
- `questionData()`：solve 阶段的 `knowledgePoints` **去掉 `role`/`evidence`**（避免暴露"哪个是核心考点"）；完整信息只在 `answerData`（judge）返回。
- `detectDistractors` 保留：仅 judge/analyze 使用。

### B3 改动 2：流水线编排（`plugins/analysis/index.js` + core）

- `geo_judge(qid, independentAnswer)`：execute 接收独立答案，返回 `{ standard: answerData, independent: <独立答案> }`，让核验有明确对照物。
- `geo_explain(qid, independentAnswer, judgeReport)`：把二者传入 `kernel.explainerData(qid, independentAnswer, judgeReport)`（函数签名本就支持，插件此前传 null），骨架内嵌"独立答案 vs 采分点"摘要。
- **渲染瘦身（效率最大杠杆）**：为 solve/judge/explain 写专用 `render`，输出**紧凑 Markdown 摘要**（仿 vision 的 `renderToMarkdown`），替代 `renderJson` 的 16k JSON dump。

### B4 改动 3：工具面收敛

- 工具描述**分级**（检索 / 讲题流水线 / 命题研究），消除歧义入口；`geo_solve` 描述明确"唯一解题入口，禁止用于浏览"。
- `geo_extract_images`：**删除**（职能已被 `geo_solve` 自动带图完全覆盖，双入口是重复调用来源）——决策点 D2；若保留，降级为"仅当 solve 未带图时显式兜底"。

### B5 改动 4：技能触发词与阶段门禁（三个技能 md）

- `geo-solver` `whenToUse` 去掉"讲题"（聚焦 怎么解/怎么做对）；`geo-question-explainer` `whenToUse` 聚焦 怎么讲/讲给学生，并在步骤 0 加硬门禁："未取得 solver 独立轨迹与 judge 核验结果前不得进入讲题"。
- 触发词表与 `docs/使用指南.md` 同步更新。

### B6 改动 5：预设层工作流路由（`agent.cordis.yml` persona / agent-instructions）

- 增加一段简短路由规则：意图→工具映射 + solve→judge→explain 顺序 + "solve 阶段读到任何答案信息视为流程违规"。

### B7 改动 6：回归门（`scripts/geo-verify.mjs`）

- 断言：`geo_solve` 返回不含 `answer/analysis`、scaffold 无 `distractorClues`；vision `extract` 降级时返回显式 `visionOk:false` + 原因（禁止空 markdown 伪装成功）；E:/C: 双副本哈希一致；视觉模型能力探测（`resolveModelInfo` 含 image）。

### B8 改动 7：P4 评测执行

- 按 `docs/讲题评测方案.md` 跑 20–30 题；**新增独立性指标**：只用 solve 阶段输出判正误与干扰项解释质量（排除 judge 污染），作为"不依赖答案"的验收门。
